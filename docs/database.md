# 数据库与迁移

## 数据模型

Drizzle 表结构定义位于 `src/worker/schema.ts`。当前 D1 结构由 `migrations/` 中全部迁移依次形成；FTS5 虚拟表与同步触发器定义在迁移 SQL 中，核对数据库行为时需要同时查阅 schema 和迁移。

1. `0000_baseline.sql` 建立书签、标签关联、设置和 FTS5 全文索引。
2. `0001_adorable_apocalypse.sql` 加入分类树及书签分类关联。
3. `0002_lucky_pretty_boy.sql` 加入分类和书签的公开/私有权限字段。

`categories.parent_id` 建立树形层级；每个书签最多属于一个分类。书签与标签通过 `bookmark_tags` 多对多关联。删除书签是软删除，永久删除会移除记录；活动、归档和回收站状态由 `archived_at`、`deleted_at` 表示。

数据库中的分类和书签权限字段默认私有，`0002` 迁移也为已有数据采用私有默认值。业务层新建内容使用设置中的默认权限，有效权限按祖先链计算，详见[架构中的权限继承](architecture.md#权限继承)。

## 索引与触发器

规范化 URL 对未删除书签建立唯一索引，因此同一 URL 可在旧记录进入回收站后重新添加。分类、标签、状态和置顶查询使用相应的 D1 索引。

`bookmarks_fts` 使用 FTS5 索引标题、描述和 URL，由数据库触发器随书签增删改同步。表结构变更时需检查相关索引与触发器，不能只修改 Drizzle schema。

## 迁移维护

- 变更表结构时同步修改 schema，并新增递增迁移；可用 `pnpm db:generate` 生成迁移后审查 SQL，确认索引、触发器与现有数据的兼容性。
- 已发布的迁移保持不变；升级按顺序应用尚未执行的 SQL，不通过重置数据库代替升级。
- 生产迁移的检查、恢复点与清单记录顺序遵循[部署流程](deployment.md#手动部署)。
- 发布期间迁移先于新代码上线，旧 Worker 必须能继续使用新 schema。字段改名、删除、类型变化等使用分阶段兼容迁移：先增加字段/结构并兼容两套读写，完成数据回填和新代码部署，确认旧版本退出后再移除旧结构。代码回滚也必须符合此兼容窗口。
- 本地使用 `pnpm db:migrate:local` 应用未执行迁移，D1 状态保存在 `.wrangler/state`；验证新库初始化与已有数据库升级路径，并运行覆盖变更的 Worker 集成测试。
- 远程迁移前的备份、目标确认与执行流程见[部署](deployment.md)。`pnpm run deploy` 不会自动应用数据库迁移。

## D1 查询预算

按 [D1 官方限制](https://developers.cloudflare.com/d1/platform/limits/)，每条 SQL 最多 100 个绑定参数、100 KB SQL 文本，最长运行 30 秒；一次 Worker 调用的 D1 查询上限为 Free 50 次、Paid 1000 次。`batch()` 中每条 SQL 仍分别受参数和长度限制，不能用批处理掩盖超限查询。

批量 ID 查询按绑定参数预算分块，为其他条件参数预留位置。分类排序最多接收 500 个 ID，存在性检查分块完成后再一次批量写入，避免后续 ID 无效时留下部分排序。文件大小限制不等于数据库预算；大批量导入/导出还要控制 SQL 次数与每页关联数据的大小，按账户方案验证可处理的数据规模。

列表应先限制有界页，再读取该页标签，避免对全部匹配记录先做关联分组。分页排序与索引同时审查，用代表性数据量的 `EXPLAIN QUERY PLAN` 判断扫描、临时排序和 FTS 路径，再在 D1 观察查询耗时与 `rows_read`；本地 SQLite 的查询计划不能代替线上延迟测量。

## 恢复验证

Time Travel 恢复会同时回退数据、schema 与迁移跟踪，恢复后重新核对 Worker 版本兼容性，不直接假定重新部署即可修复。核对分类层级、书签活动/归档/回收站数量、标签关联、私有祖先权限和全文搜索；修改 FTS 结构时验证虚拟表与全部同步触发器一致。

备份范围、FTS5 导出限制、原库恢复与代码回滚的命令和边界统一见[备份、恢复与回滚](deployment.md#备份恢复与回滚)。
