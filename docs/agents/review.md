# 重构验证与审查交接

合并写入锁、取消或缓存状态时，先读下方的场景验证；准备代码审查或交付时，按交接步骤固定范围。Git 授权和必需检查由根 [AGENTS.md](../../AGENTS.md) 规定。

## 合并异步状态时的验证

把多个入口收进同一 module 前，列出它们原先可以并行执行的操作，以及共享状态后允许执行、合并等待或明确拒绝的操作。不同命令、不同输入不能仅因作用于同一对象就被当成重复意图。

以真实调用入口和现有测试 adapter 验证以下受影响的交错场景，用可控 Promise 固定完成顺序：

| 场景                                 | 验证结果                                                   |
| ------------------------------------ | ---------------------------------------------------------- |
| 同一对象重复提交                     | 不产生重复请求，并验证调用者收到的结果或反馈               |
| 同一对象提交不同命令或不同输入       | 按约定执行、等待或明确拒绝；不会正常返回却丢弃操作         |
| 不同对象同时提交                     | 保留约定的并行能力，冲突不影响其他对象                     |
| 原请求成功或失败后重试               | 释放对应保护，重试可执行；冲突拒绝不会提前释放原请求的保护 |
| 请求期间卸载、切换身份或切换缓存目标 | 迟到结果按生命周期约定处理，不污染新内容或草稿             |

断言实际请求、返回或错误、草稿保留及刷新副作用，避免只检查 pending 标志。修复竞态时，先让复现用例在原实现上失败，再验证修复及重试；不依赖固定延时制造时序。书签写入可从 [useBookmarkMutations 测试](../../test/unit/web/features/bookmarks/useBookmarkMutations.test.tsx)和[重复提交测试](../../test/unit/web/features/bookmarks/useBookmarkMutations.pending.test.tsx)扩展，沿用前后台真实共享的调用入口。

## 审查与交接

1. 开发开始记录起点提交。交接前固定比较基点和目标提交的 SHA；若期间合入主分支，以最终合入的主分支提交为基点，确认差异仅覆盖约定任务。合并回主分支前完成固定，避免之后用 `main...HEAD` 得到空差异。
2. 记录需求依据：Issue、仓库文档路径，或本轮用户已确认的目标与约束摘要。临时 HTML 可以辅助阅读，关键约束同时保留在交接说明或对应职责文档中。
3. 交付说明包含 `审查范围：<base SHA>...<target SHA>`、需求依据、实际验证结果及未完成项。多阶段任务明确本次范围包含哪些阶段；纯文档任务按文档验证标准交付。
4. 审查优先沿用用户已确认的范围和需求依据。仅在范围存在歧义、提交无法解析或缺少关键需求时补充询问；新增任务重新确定范围。

读取固定差异用 `git diff <base SHA>...<target SHA>`，提交列表用 `git log <base SHA>..<target SHA> --oneline`。审查共享状态的变更时，对照上表和原调用路径核对行为；已经能由测试或工具确定的问题通过自动检查约束。
